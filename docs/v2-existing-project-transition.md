# Переход на v2 в существующем Supabase-проекте

> **Current policy — 2026-10-30:** V1 is retired. Any requirement below to keep
> its client/API working, defer retirement to R3 or verify v1 before releasing v2
> is superseded by [v1-retirement.md](v1-retirement.md) and [AGENTS.md](../AGENTS.md).
> Auth/accounts and historical rows stay; v1 compatibility and parallel operation
> are not release requirements. Run `disable-v1.sql` on the existing project.

Актуальное решение от 27.10.2026: использовать проект
`your-project-ref`, без создания новой базы и без сброса Supabase Auth.
Этот документ заменяет прежние требования о новом проекте/удалении аккаунтов.
Подготовка перехода не выполняет SQL на рабочей базе и не переключает сайт.

## Политика выпуска от 28.10.2026

Решение владельца, заменяющее прежние условия в #305, #325, #327 и в
[плане](vocabulary-implementation-plan.ru.md):

- **Объём первого выпуска.** Публикуется v2 с одной законченной функцией:
  изучение и повторение слов. Остальные семейства упражнений (M1–M8) и E9 не
  блокируют выпуск и переносятся после него. Пункт R3 «новая версия с одним
  словарём не публикуется» снят. Меню не должно показывать нереализованные
  разделы как работающие.
- **Старую версию не поддерживаем.** Все прежние пользователи были тестировщиками.
  После переключения v1 не остаётся запасным продуктом; ради отката v1 не
  сохраняется.
- **Что сбрасывается.** Только данные v1: `public.progress`, `public.daily_stats`,
  `public.srs_cards`. Аккаунты `auth.users`, связи Google и настройки Auth
  остаются, поэтому тестировщикам не нужно регистрироваться заново. Сброс данных
  Auth по-прежнему не выполняется.
- **Что остаётся обязательным до выпуска:** S3 (#295), подключение главной v2 к
  Auth и серверному каталогу (см. «Граница L4»), применение `transition.sql` и
  `learning.sql`, деплой функций, живая проверка Google-входа и записи ответа,
  резервная копия прикладных данных.
- **Порядок в R3.** Сначала переключается клиент и поколение кеша, затем
  закрываются старые RPC и права записи v1, и только после этого, отдельным шагом,
  очищаются данные v1. Очистка необратима и выполняется только по явному
  подтверждению владельца на момент действия; одно это решение её не разрешает.

## Что сохраняем

- Существующие аккаунты `auth.users`, связи Google в Auth и настройки провайдера.
- Текущие Site URL и разрешённые redirects. Для preview добавляется только
  конкретный callback v2, без замены списка.
- Данные `public.progress`, `public.daily_stats`, `public.srs_cards`, их RLS,
  grants и пять действующих RPC до отдельного этапа отключения v1.
- Текущий публичный клиент до переключения в R3 (по политике от 28.10.2026 для
  переключения достаточно готовой функции изучения и повторения слов).

Новые таблицы каталога, его версии, колоды и метаданные поколения добавляются
рядом с v1. Прогресс v2 начинается отдельно; автоматического преобразования
старых счётчиков в компонентный SRS нет. Это не удаляет старую историю.
Auth-ID остаются прежними, но ключи Auth/IndexedDB/outbox v2 имеют свой namespace.
Временное соседство схем обеспечивает подготовку, а не два постоянных продукта.

## Проверка действующего проекта

27.10.2026 через SQL Editor выполнен только `SELECT` инвентаризации. В `public`
есть `progress`, `daily_stats`, `srs_cards` с RLS и пять RPC:
`upsert_progress`, `sync_progress`, `increment_daily`, `sync_daily`, `sync_srs_card`.
`catalog_private` и `v2_environment` отсутствуют; имена нового каталога свободны.
Это снимок проверки, а не гарантия отсутствия изменений перед будущим применением:
preflight повторно проверяет конфликты внутри транзакции.

## Подготовленные файлы

```sh
npm ci
npm run build
node --env-file=config/v2/existing-preview.env.example scripts/prepare-v2-deployment.mjs
```

Профиль содержит только уже публичные URL/ключ проекта. Адрес начального
предпросмотра — `https://drillcards.org/v2/environment.html`; главная v1 остаётся
на прежнем адресе. При выборе другого preview-хоста измените `V2_SITE_URL` в
личной копии профиля и добавьте соответствующий точный redirect.
Не храните Google secret, service-role key или пароль БД в публичном профиле.

Результат в `build/v2/preview/` (gitignored):

| Файл | Назначение |
| --- | --- |
| `inventory.sql` | Только чтение: текущие объекты, RLS, сигнатуры RPC и число аккаунтов |
| `transition.json` | Проект, commit, каталог, epoch и явные признаки сохранения Auth/v1 |
| `transition.sql` | Одна атомарная транзакция: preflight → новая схема → seed → метаданные |
| `learning.sql` | Forward-миграция S1 (#319) после `transition.sql`: журнал событий, проекция и commit-RPC ([learning-sync.md](learning-sync.md)) |
| `learning-items.sql` | Forward-миграция G3 (#332) после `learning.sql`: цели упражнений семейств в том же журнале |
| `item-datasets.sql` | Публикация версий наборов из `public/data/items/` (ровно тех файлов, что отдаёт сайт); идемпотентна, другая версия с тем же номером отклоняется |
| `supabase/` | Только Edge Function/config для адресного деплоя функции |

Папка CLI намеренно не содержит migrations/seed/Auth config. Не применяйте к
существующему проекту `db reset`, `db push` или `config push` из этой папки.
Их автоматическое применение могло бы затронуть историю миграций или глобальные
настройки Auth. Инструмент подготовки ни одну из этих команд не запускает.
Старые миграции 001–007 повторно не исполняются и не записываются в историю CLI.

`catalog:bootstrap` остаётся отдельным инструментом для пустого тестового проекта;
его fresh-preflight по-прежнему отказывает на базе с таблицами v1. Для текущего
проекта используйте именно `transition.sql`, а не свежий bootstrap.

## Будущее применение подготовленного перехода

Это отдельный шаг после проверки PR и конкретного SQL. В рамках подготовки
ни одна из следующих команд на рабочем проекте не выполнялась.

1. Зафиксировать release commit/артефакты, убедиться в наличии пригодной резервной
   копии прикладных данных и способа вернуть предыдущую статическую сборку.
   Экспорт хранить вне репозитория. Auth не пересоздавать и не восстанавливать
   вручную через удаление внутренних таблиц.
2. Проверить, что соединение `V2_DATABASE_URL` действительно ведёт в
   `your-project-ref` (host прямого соединения или project-ref в имени пользователя
   pooler). SQL не может надёжно вывести hosted project-ref из `current_database()`;
   одного имени `postgres` для проверки назначения недостаточно.
3. Выполнить `inventory.sql`, сверить его с планом и сохранить результат проверки.
4. Применить проверенный `transition.sql` через административное соединение:

```sh
psql "$V2_DATABASE_URL" --set ON_ERROR_STOP=on --file build/v2/preview/inventory.sql
psql "$V2_DATABASE_URL" --set ON_ERROR_STOP=on --file build/v2/preview/transition.sql
```

Preflight берёт транзакционную блокировку и отказывает при существующем каталоге
или конфликте имён. Не выполняются DROP/TRUNCATE, изменение Auth, перенос старого
прогресса или изменение действующих RPC. При ошибке транзакция откатывается целиком.
Повторное применение завершённой установки отказывает без перезаписи данных;
дальнейшие изменения выполняются отдельными forward-миграциями.
Новые версии seed после установки применяются диффом через `npm run catalog:import`
(#356), см. [catalog-schema.md](catalog-schema.md#seed-updates-on-a-live-catalog-356).

5. Применить forward-миграцию S1 тем же административным соединением. Её preflight
   требует уже установленный каталог и отказывает при существующих таблицах обучения;
   она закрепляет текущий импорт как snapshot каталога и не переносит старый прогресс:

```sh
psql "$V2_DATABASE_URL" --set ON_ERROR_STOP=on --file build/v2/preview/learning.sql
```

6. Применить миграцию упражнений семейств и опубликовать их наборы. Без второго
   файла приём событий отклоняет любой ответ на страницах семейств
   (`unknown-dataset`). Повторное применение `item-datasets.sql` ничего не меняет;
   при изменении набора в `public/data/items/` нужна новая версия набора и новый
   прогон этого файла до публикации сайта:

```sh
psql "$V2_DATABASE_URL" --set ON_ERROR_STOP=on --file build/v2/preview/learning-items.sql
psql "$V2_DATABASE_URL" --set ON_ERROR_STOP=on --file build/v2/preview/item-datasets.sql
```

## Вход и preview

Google-провайдер и его секрет остаются в существующем проекте. Backend callback
`https://your-project-ref.supabase.co/auth/v1/callback` сохраняется. Новый OAuth
client и новый пароль базы для этого перехода не требуются.

В существующий список Supabase Auth redirect URLs нужно **добавить**
`https://drillcards.org/v2/environment.html`, сохранив текущие значения и Site URL.
Перед изменением сохранить исходный список. Если провайдер ещё не настроен,
это отдельная настройка; подготовка не выдаёт наличие клиентского кода за
проверенный реальный Google-вход.

Развёртывание новой диагностической функции адресуется существующему проекту:

```sh
supabase --workdir build/v2/preview secrets set --project-ref your-project-ref --env-file /path/to/v2-functions.env
supabase --workdir build/v2/preview functions deploy v2-health --project-ref your-project-ref
```

Функция приёма событий S1 (`v2-learning-events`) деплоится так же, только после
`learning.sql`. Ключ service-role она берёт из стандартного окружения Edge Functions
(`SUPABASE_SECRET_KEYS`/`SUPABASE_SERVICE_ROLE_KEY`) и никогда не отдаёт браузеру:

```sh
supabase --workdir build/v2/preview functions deploy v2-learning-events --project-ref your-project-ref
```

В приватной копии `functions.env.example` нужны только `V2_ENVIRONMENT=preview`
и `V2_ALLOWED_ORIGINS=https://drillcards.org`. Значения Google/DB не копируются
в секреты функции. Другие функции и настройки провайдера не заменяются.

Для статической сборки после обычного `npm run build`:

```sh
node --env-file=config/v2/existing-preview.env.example scripts/build-v2-environment.mjs
node --env-file=config/v2/existing-preview.env.example scripts/v2-smoke.mjs
```

Smoke запускать после фактического применения схемы и деплоя функции. Он проверяет
гостевой доступ; для проверки участника можно приватно передать
`V2_TEST_ACCESS_TOKEN`. Токен не печатается и не записывается в артефакты.
После публикации проверить реальный Google-вход, выход, отсутствие чужих личных
колод и отказ старого API после disable-v1.sql. Убедиться, что число аккаунтов/старые данные
сохранились. Сам факт зелёных локальных тестов эту живую приёмку не заменяет.

## Выпуск только v2

V1 удалена из клиента и сборки. `DRILLCARDS_SITE_ENTRY=v1` отклоняется; отсутствие
переменной больше не включает старую версию. Для размещения настроить V2_* и
согласовать серверные метаданные/Edge Functions с выбранным окружением. Cloudflare
сборка без настроенного backend отказывает, чтобы не подменить рабочий сервис
локальной гостевой демонстрацией. Локальная сборка без V2_* остаётся доступна
для разработки и тестов.

Сборка публикует перенаправления `/`, `/index.html`, `/de`, `/de/*` на `/v2/session`.
Новый worker обслуживает только v2 и использует отдельное поколение кеша.
Старые регистрации/кеши убираются до загрузки модулей v2. Офлайн-каталог и
изоляция аккаунтов v2 сохранены.

Отключение старого API выполняется через
`supabase/v2/transition/disable-v1.sql` и проверяется
`supabase/v2/transition/r3-cutover-check.sql`. Инструкция:
[v1-retirement.md](v1-retirement.md). Старые вкладки не смогут отправить
прогресс, даже если ещё не получили новый клиент. Аккаунты, Google-настройки
и архивные строки сохраняются. Возвращать поддержку v1 для отката не нужно;
откатывать следует только к совместимой сборке v2.

В одном проекте одна строка `v2_environment`. Переход preview → production
согласованно меняет сервер, клиент и функции; второй backend не создаётся.
Подготовка SQL и успешные локальные проверки не означают его применения
на рабочем проекте или фактической публикации.

## Локальные доказательства

Тесты исполняют реальные миграции v1, заполняют Auth/Google identities и три
таблицы старой истории, затем применяют **тот же сгенерированный transition.sql**.
Проверяются полное сохранение строк, архивных строк при добавлении каталога и отказ API после disable-v1.sql, 1306 слов/8 колод, отказ при коллизии и повторном запуске,
полный rollback при ошибке после загрузки seed. Проверки SDK/PKCE/выхода и
контроль старого service-worker кеша остаются в общем локальном наборе.

## Граница L4

Выполнено в R1a (#325): главная `/v2/session.html` и восемь страниц семейств
открывают ту же конфигурацию, проверяют epoch сервера и пишут в scope аккаунта
вошедшего пользователя; после каждого сохранённого ответа запускается
`SyncService`. Опубликованный каталог слов (его доступом) читает главная; страницы
семейств пока берут наборы из `public/data/items/`, поэтому перед выпуском их версии
должны совпадать с импортированными в `catalog_private.item_datasets`. Смена владельца
перезагружает страницу, что отменяет активное занятие. Статический seed остаётся
только локальным fallback; ошибки настроенного backend показываются.
Подробности: [v2-environments.md](v2-environments.md#page-wiring-r1a).
