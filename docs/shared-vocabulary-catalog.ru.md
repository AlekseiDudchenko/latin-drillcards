# Общий каталог: добавление слов и проверка контента

Статус: проект дополнения к [архитектуре словаря](vocabulary-architecture.ru.md).
Уточнение требований от 22.10.2026. Функция пока не реализована.

## 1. Принцип

Пользователь добавляет слово в **общедоступный пул**, а не в собственную
изолированную копию словаря. Слово может добавляться в личные/общие колоды,
но имеет один canonical wordId. Прогресс принадлежит пользователю и этому ID.

Первый ввод запускает поиск переводов и примеров в публичных источниках.
Пользователь проверяет каждый принимаемый элемент; загруженные варианты
не публикуются автоматически. Подтверждения верификации не являются
правильными ответами в упражнении и не повышают SRS.

В пуле есть кандидаты и опубликованные слова. По умолчанию пользователи
тренируются только на опубликованном содержании. Кандидаты доступны в
отдельном разделе «Помочь проверить», с явным статусом.

## 2. Пользовательский поток

1. Ввести немецкое слово/выражение. Интерфейс заранее сообщает, что оно
   пополнит общий каталог и будет отправлено внешним словарным источникам.
2. Найти совпадения в каталоге: показать часть речи, артикль и значение.
3. Если нужное значение уже опубликовано, добавить его ссылку в выбранную
   колоду. Не создавать копию и не обращаться к источникам повторно.
4. Если его нет, создать идемпотентный запрос enrichment и показать найденные
   значения. Пользователь выбирает нужное; разные значения получают разные ID.
5. Показать форму проверки: слово/часть речи/артикль, отдельно каждый перевод,
   отдельно каждый пример с его переводами и ссылками на источники.
6. Для каждого элемента доступны «Подтвердить», «Исправить», «Отклонить» и
   «Проверю позже». Последнее не считается подтверждением.
7. Перед публикацией показать, какие элементы будут общедоступны и какие
   остались непроверенными. Публиковать только явно подтверждённые ревизии.
8. Добавить опубликованный wordId в выбранную колоду добавившего пользователя.
   У остальных пользователей слово доступно в общем поиске; в их колоды
   автоматически не включается.

Полный просмотр публичных слов возможен без входа. Добавление, подтверждение
и публикация требуют входа, чтобы иметь проверяемую историю вклада. Гость
может подготовить локальный черновик, а отправить после входа.

## 3. Проверка по отдельным элементам

| Элемент | Что пользователь подтверждает |
| --- | --- |
| Значение слова | Написание, часть речи, артикль при наличии, выбранный смысл |
| Каждый перевод | Язык, соответствие выбранному смыслу, допустимость в упражнении |
| Каждый немецкий пример | Грамматику, естественность и употребление в нужном значении |
| Каждый перевод примера | Соответствие конкретному немецкому предложению |

Существуют отдельные статусы pending / confirmed / rejected / superseded.
Review ссылается на тип элемента, его ID, revisionId и contentHash. Есть
reviewerId, время и решение. Модель не ограничивается boolean verified у слова.

У примера дополнительно проверяется связь с выбранным senseId: грамматически
верное предложение с другим значением слова не становится подходящим примером.
Новая языковая версия перевода требует собственной проверки. Подтверждение
немецкого предложения не подтверждает автоматически все его переводы.

При исправлении создаётся новая ревизия, которую пользователь подтверждает
после просмотра. Редактирование после подтверждения отменяет применимость
старого решения к новой ревизии. Подтверждённые другие примеры не сбрасываются.
Текущая опубликованная версия остаётся доступной, пока новая не принята.

Для первого выпуска достаточна явная проверка одним вошедшим пользователем,
в том числе добавившим. Интерфейс пишет «Подтверждено участником», не
«Проверено экспертом». Независимая проверка другим участником и жалобы
поддерживаются моделью, но не обязательны для каждой первой публикации.

Нельзя иметь одну кнопку, автоматически отмечающую весь импорт проверенным.
Итоговая кнопка «Опубликовать подтверждённое» не заменяет отдельных решений.
Если пользователь пропускает часть примеров, они остаются кандидатами и
не попадают ни в опубликованную карточку, ни в задания, ни в отвлекающие ответы.

Минимум публикации: подтверждённое значение и хотя бы один подтверждённый
перевод. В начальной версии запрашиваем до трёх коротких примеров, каждый
включается только после проверки. Отсутствие примеров не превращается в
вымышленное наполнение; можно завершить их проверку позднее.
Нет обязательного требования иметь одновременно RU и EN: задания доступны
для языков с подтверждёнными переводами.

## 4. Источники и происхождение

Начальные адаптеры:

| Адаптер | Данные | Особенности |
| --- | --- | --- |
| Wiktionary | Лексема, часть речи, артикль, значения, доступные переводы | MediaWiki API даёт страницу/ревизию; отдельный parser извлекает структуру конкретной языковой редакции |
| Tatoeba | Немецкие предложения и связанные переводы | Используем актуальный API, сохраняем ID предложения и каждого перевода; проверяем связь пары |

Наличие публичного API не означает гарантированного наличия перевода RU/EN,
подходящего смысла или безошибочных примеров. Результат — кандидаты.
Не используем старый api_v0 Tatoeba для новой реализации.

Для каждого заимствованного текста сохраняются provider, sourceId,
sourceRevision/хеш, sourceUrl, author/attribution, license, fetchedAt и
сведения о пользовательских изменениях. Предложение, его перевод и
лексикографическое описание могут иметь разные источники и лицензии.

У Tatoeba для текстов по умолчанию указана CC BY 2.0 FR; встречается CC0.
Аудио лицензируется отдельно и не импортируется автоматически вместе с
текстом. Атрибуция текста включает автора и ссылку на конкретный источник.
Wiktionary указывает CC BY-SA 4.0 для собственного текста; отдельные
внешние цитаты/материалы могут иметь другие условия. Для примеров на первом
этапе используем Tatoeba, не копируем произвольные цитаты из словарных статей.

Публикация сохраняет применимые условия каждого элемента и отображает
короткую ссылку «Источник»; экспорт передаёт атрибуцию/лицензию вместе с текстом.
Подтверждение пользователем проверяет качество, но не меняет лицензию источника.
Не переобозначаем импорт единым CC0 или иной лицензией всего приложения.
Для ручных вкладов и переработанных текстов условия публикации должны быть
определены и показаны до отправки; адаптеры не допускают материал с неизвестными
условиями повторного распространения в опубликованную версию.

Официальные страницы, проверенные при проектировании:

- https://www.mediawiki.org/wiki/API:Action_API
- https://de.wiktionary.org/wiki/Tisch — пример структуры значений/переводов и footer лицензии.
- https://en.wiktionary.org/wiki/Wiktionary:Copyrights — собственный текст и внешние материалы.
- https://en.wiki.tatoeba.org/articles/show/api
- https://api.tatoeba.org/
- https://en.wiki.tatoeba.org/articles/show/using-the-tatoeba-corpus
- https://tatoeba.org/en/downloads

Перед интеграцией проверяются текущие контракты API и лимиты источников;
список выше не задаёт неограниченную квоту или SLA.

## 5. Серверная обработка первого добавления

Браузер вызывает наш backend, backend — только настроенные публичные
источники. Прямые вызовы словарей из каждой карточки не нужны.

`requestWord` возвращает existing / fetching / needs-review / partial /
failed с canonicalId/candidateId или jobId.

- Сначала поиск в каталоге и кеше. Нормализация Unicode/пробелов не уничтожает
  регистр, артикль, часть речи и различия значений немецкого слова.
- Первичный lookup кешируется по языку, нормализованной лексеме и версии
  адаптера. Он может вернуть несколько значений. Материалы связываются
  с выбранным canonical sense; переводная строка не является ключом смысла.
- Уникальный активный job/lease объединяет одновременные запросы. Создание
  canonical word и привязка источников транзакционны: два пользователя
  получают тот же ID после выбора одинакового смысла.
- Неопределённые дубликаты требуют выбора/проверки, не объединяются по
  совпадению написания. Слияние позднее имеет aliases, не ломает прогресс.
- Источники запрашиваются при первом добавлении; повторный запрос использует
  результат и job, а не запускает новый fetch для каждого пользователя.
- Догрузка отсутствующего языка, явное обновление или исправление источника
  создают отдельный job и новые pending-ревизии. Они не перезаписывают
  проверенные тексты автоматически.
- Временная ошибка имеет retry/backoff и повторно используемый jobId;
  «не найдено» кешируется на ограниченный срок, а не навсегда.
- Ошибка одного провайдера не теряет результат другого: partial сохраняется,
  интерфейс показывает недостающие данные и возможность повторить/дополнить.

Публикация — отдельная атомарная операция с expectedRevision: проверяются
полнота, решения по текущим хешам, права участника и условия источников,
затем формируется новая опубликованная read model. Другой пользователь не
может подменить текст между просмотром и подтверждением.

Новый пользовательский текст хранится как ограниченный по размеру plain text,
без доверенного HTML. Сервер применяет лимиты запросов/публикаций и проверяет
валидность схемы. Адреса внешних запросов задают адаптеры, не произвольный URL
из пользовательской формы.

## 6. Каталог, версии и права

Авторитетный общий каталог хранится в Supabase. Исходные JSON переносятся
как seed-данные в новую схему v2 внутри существующего проекта. Auth сохраняется,
старый прогресс хранится отдельно и не импортируется в компонентный SRS;
могут остаться публичные snapshots для быстрого старта и
офлайн-кеша. Новые слова публикуются без сборки сайта или GitHub Actions.
Поиск и разрешение ссылок новых слов используют серверный каталог и локальный
кеш. Совместимость с прежним word-index, старыми slug/маршрутами не требуется.

Публично читается только опубликованная read model. Очередь кандидатов —
отдельное представление для вошедших участников, без внутренних аккаунтных
данных, provider credentials и сырых служебных ответов. Прогресс и личные
наборы остаются закрытыми RLS по владельцу.

Основные таблицы: words, word_revisions, word_translations, examples,
example_translations, word_examples, content_sources, content_reviews,
enrichment_jobs. Полная история редактирования/проверок версионирована.
Клиент не имеет универсального update на опубликованный контент: изменения
идут через contribution/review/publish. Удалить слово из своей колоды означает
убрать membership, а не удалить общее слово у остальных пользователей.

Сессия фиксирует contentRevision до начала заданий. Исправление общего
перевода не меняет уже показанный вопрос и не обнуляет чужой прогресс.
Смена смысла создаёт новое слово, обычная корректировка — новую ревизию.
Отозванный ошибочный допустимый ответ не используется в новых заданиях;
старые оценки остаются с прежней версией, переоценка — только отдельной политикой.

## 7. Проверки готовности

- Два одновременных добавления одной лексемы не дублируют запрос провайдера
  и canonical word для одного смысла; разные смыслы не сливаются.
- Существующее опубликованное слово добавляется в колоду без нового fetch.
- Подтверждение одного примера не подтверждает соседние примеры/переводы.
- Изменение текста после просмотра/подтверждения требует новой проверки.
- Пропущенный или отклонённый текст не попадает в публичные упражнения.
- Подтверждение автором обозначено именно как проверка участником.
- Отсутствие EN не блокирует RU-задание; непроверенный EN не используется.
- Partial/timeout/reload не теряют кандидата, повтор не создаёт второй job.
- Новый пример не подменяет текущую проверенную версию без принятия.
- Источник, автор, ревизия и лицензия сохраняются отдельно для каждого текста
  и доступны при показе/экспорте.
- Новое слово можно найти и изучать без новой сборки сайта.
- Публикация и проверка слова не увеличивают SRS или число учебных ответов.
- Один wordId из общего пула имеет один прогресс пользователя во всех колодах.

Реализация добавляется в существующий PR архитектуры как проект решения;
сам этот документ не выполняет внешние запросы за словами и не публикует
контент пользователей в рабочий каталог.
